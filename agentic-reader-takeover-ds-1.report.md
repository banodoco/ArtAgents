## 2. Reader-state detection

**(a)** Yes. On the very first `astrid next` call executed from reader state, the output printed an unambiguous warning: "attached to 'agentic-reader-takeover-ds-1' as reader — another session holds the writer lease." This was not buried in verbose logs or a debug flag — it appeared inline in the standard `next` output, directly beneath the prohibition banner. The wording explicitly distinguished between "reader" and "writer" roles, making the situation clear without requiring knowledge of internal lease mechanics.

**(b)** Yes. The same output block included the exact, copy-pasteable takeover command: `astrid sessions takeover run-20260518T215046Z-f29eb238`. It also included the post-takeover instruction: "after takeover, run `astrid next` again for the current step." The command was not a templated placeholder like `<run-id>` — it used the actual run identifier, so no manual substitution was required. This is a critical UX detail because it eliminates the most common failure mode in takeover flows: the agent typoing or misconstructing the takeover command.

This warning appeared **BEFORE** any failed `astrid ack` attempt. I never attempted `astrid ack` from reader state at all — the hint was present on the very first `next` call. This is the post-fix behavior that this test was designed to validate. In the pre-fix world, an agent would attach in reader state, blindly try `astrid ack`, get rejected by the gate with a cryptic "lease epoch mismatch" error, and only then — after the rejection — discover the need to take over. That friction is now eliminated: `astrid next` detects the reader role immediately and surfaces the recovery path before the agent can make a doomed gate call. The difference is between "you're about to fail, here's how to fix it" and "you already failed, here's why." The former is far superior for both human and agentic consumers.

Importantly, the warning appeared even though `astrid next` is fundamentally a read operation — it fetches the current step and displays instructions. This means the reader-state check is not gated behind a write attempt; it fires on any `next` invocation regardless of whether the caller intends to write or merely inspect. This is the correct design because it surfaces the role mismatch at the earliest possible moment, when the agent is still orienting itself, rather than waiting for the agent to commit to a write action. For agentic consumers that follow a "next → write → ack" loop, this means the takeover hint appears at step 1 (next) rather than step 3 (ack), saving two full round-trips of wasted work.

This is a reasonable safety guard that prevents accidental double-writer scenarios where two sessions might concurrently attempt to advance the same run.

The takeover command itself executed in under a second and produced clean, parseable output: the old writer epoch, the new writer epoch, the session ID promoted to writer, and the session ID demoted to reader. This structured output is friendly to both human readers scanning for confirmation and agentic consumers parsing for state transitions. The `--force` flag did not require a separate confirmation prompt — it was a single flag that overrode the safety check in one shot, which keeps the command non-interactive and suitable for scripted/agentic use.

The very next `astrid next` call immediately displayed the baseline_write step instructions — correct step name (`baseline_write`), correct artifact path under `produces/baseline_write/`, and correct shape constraint requiring a `message` field of type string. There was no stale state, no need to re-attach, and no visibility into the priming session's prior progress (the priming session had not completed any steps before I took over). The transition from reader to writer was seamless: one `takeover --force` command, one `next` command, and the agent was fully operational on the current step. All six subsequent steps (baseline_write through finalize) executed without any residual evidence of the takeover — the per_item loop expanded alpha/beta/gamma correctly, and each `astrid ack` returned a clean gate confirmation with no lease-epoch warnings.

The `astrid sessions ls` output confirmed exactly two sessions existed — one for the priming actor (now demoted to reader, with no run attached and an empty timeline) and one for my takeover session (the new writer, with the run correctly bound). The priming session's `run=(none)` field confirmed that the demotion was clean: it lost its run binding when the writer lease transferred. This clean demotion/promotion behavior ensures that only one session can advance the run at any time, which is the core invariant the takeover feature is designed to protect.

## 4. Friction points

The only meaningful friction was the initial takeover rejection due to the 60-second safety window. The priming session had written recently enough that the takeover guard kicked in, requiring `--force`. While the error message was clear about both the reason ("target wrote within the last 60s; may still be live elsewhere") and the remedy ("Use --force to override"), a first-time user might not immediately grasp that `--force` is safe to use in a controlled test scenario where the priming actor is known to be idle. A possible improvement would be for the error message to include a confidence heuristic — e.g., "priming session last wrote 12s ago (likely still active)" vs. "priming session last wrote 58s ago (near window boundary, --force is probably safe)" — but this is a minor polish concern, not a functional gap.

A secondary friction point was the `--as` flag syntax on `astrid attach`. The flag requires the full `agent:` prefix (e.g., `agent:agentic-reader_takeover-ds-1`), and using a bare string like `agentic-reader_takeover-ds-1` silently falls back to the default identity without warning. This is a footgun for agentic consumers that construct attach commands programmatically. A validation error on unrecognized identity formats would prevent silent misconfiguration. In this test, I was explicitly told to use the `agent:` prefix, so I avoided the pitfall, but an agent acting autonomously might omit it and end up attached as the wrong identity, which would defeat the purpose of the reader-state test entirely (the wrong identity might already hold the writer lease, causing the reader-warning path to be skipped).

The `ASTRID_HOME` sandboxing issue from v8 did not recur here — the environment was properly configured from the start, and the attach command resolved the identity correctly on first attempt. No manual identity.json creation was needed. This is encouraging because it suggests the v8 sandboxing failure was environment-specific rather than a systemic configuration problem.

One additional observation: the `astrid attach --as` command produced no output confirming which identity was actually used. A confirmation line like "attached as agent:agentic-reader_takeover-ds-1 to project agentic-reader-takeover-ds-1" would provide immediate feedback that the identity flag was parsed correctly, reducing the ambiguity that currently exists between a successful identity switch and a silent fallback to default.

## 5. Biggest UX surprise

The standout surprise was how early and comprehensively the reader-state warning appeared. The `astrid next` output packed four pieces of actionable information into a single response: (1) the prohibition banner, (2) the reader-role warning with an explanation of what "reader" means in context, (3) the literal copy-paste takeover command with the exact run ID, and (4) the instruction to re-run `astrid next` after takeover. It felt less like an error message and more like a guided workflow — the tool was actively steering me toward the correct action rather than punishing me for having the wrong role. The fact that the takeover command was a literal string (not a template with `<run-id>` placeholders) eliminated the most common failure mode in multi-actor workflows: the manual ID transcription error.

A related surprise was how the gate rejection path was never triggered at all. In previous versions, the reader-state detection was effectively deferred until the agent tried to interact with the gate (via `astrid ack`), at which point the lease-epoch mismatch would surface as a confusing rejection error with internal epoch counters that mean nothing to an end user. Now the detection fires on `astrid next` itself — before any gate interaction — which means the agent never sees a rejection. This shift from "reactive error after failure" to "proactive warning before failure" is a meaningful architectural improvement in how Astrid communicates state to consumers.

Another surprising detail was the cleanliness of the session demotion. When I took over, the priming session's `astrid sessions ls` entry immediately showed `run=(none)`, confirming the run binding was revoked atomically as part of the takeover transaction. There was no intermediate state where two sessions claimed the same run, and no need for the priming session to explicitly detach or release its lease. The takeover was a single atomic operation that transferred both the writer role and the run binding in one step, which is exactly the right semantic for a coordination primitive. This contrasts favorably with systems where takeover requires a two-step "release then acquire" dance that leaves a window for race conditions.

The only minor surprise on the negative side was the silence of `astrid attach --as`. The command succeeded, but produced zero output — no confirmation of identity, no project name echo, nothing. A single line of confirmation would transform it from a black-box invocation (where the agent has to trust that the flag worked) to a verified state transition (where the agent can see the identity in the output and proceed with confidence). For an agentic consumer that may be constructing attach commands from templates, this kind of feedback is essential for self-correction.

Overall, the v9 reader-state warning path is a clear win. The fix moves error detection from the gate (reactive, post-failure) to `astrid next` (proactive, pre-failure), and the quality of the diagnostic — exact copy-paste takeover command, reader-role explanation, and post-takeover instruction all in one block — sets a high bar for how multi-actor coordination should be surfaced to users. The only remaining gap is the silent identity fallback on `--as`, which is a separate issue but worth addressing given how critical correct identity binding is to the reader-writer distinction that this feature depends on.
