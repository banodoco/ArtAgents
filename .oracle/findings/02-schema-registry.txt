## Findings (ranked)

**1. Default executor registry omits the override store — VERIFIED.** `load_default_registry()` builds `ExecutorRegistry(alias_resolver=resolver)` with no `override_store=` (`execution/executor/registry.py:264`). Only the CLI patches it post-hoc (`executor/cli.py:90-95`); same pattern in orchestrator (`cli.py:92-98`) and element (`element/cli.py:37-44`). All non-CLI consumers (`argv.py:23`, runner, api) call `load_default_registry()` bare → `get()` override remap (`registry.py:126-132`) silently inert there.

**2. Schema vs normalizer: in sync today, but dual-path.** `pack.json` (Draft-07, `additionalProperties:false`) is enforced only by `pack/validate.py:362` (PackValidator). Runtime discovery `loader.load_pack_manifest()` (`loader.py:110-152`) hand-normalizes via `permissions.py` `_optional_pack_aliases`/`_normalize_pack_permissions` — independently mirroring schema rules (alias kinds `PACK_ALIAS_KINDS=("executor","orchestrator")`, `_common.py:40-41`; permission ids `_common.py:42-49`). Both reject unknown keys; patterns agree (`_defs.json:9-11` vs `_common.py:55`). Drift risk is real but currently none.

**3. CapabilityRegistry** (`registry/base.py`): keyed `dict[K, list[T]]`, priority-sorted (`_register_impl:88-106`), winner=index[0], conflicts via `conflicts():168-185`. `kind` is only a filter in subclass `list()` (`executor/registry.py:141-148`); `_resolve_override_key` is generic (`base.py:134-148`).

**4. Override admin:** `_cmd_override` (`cli_handlers.py:586-601`) → `OverrideStore.set_override("executor", id, target)` (`override.py:38-49`), persisted to `<project>/astrid/packs/local/.overrides.json` (`override.py:80-81`). Semantics: from → to remap at `get()` time.

## Verified facts
- pack.yaml fields: id/name/version, content roots (executors/orchestrators/elements/schemas/examples/docs), aliases (kind enum executor|orchestrator), permissions, extensions, secrets, dependencies.
- Aliases: per-pack declared, registered via `extract_pack_aliases`/`_register_pack_aliases` (`alias_resolver.py:193-229`), transitively resolved with cycle checks (`:109-125`).

## Unknowns
- No `renderer` anywhere: content key, alias kind, `_defs`, loader walkers, schemas/v1/renderer.json all absent.

## Risks
- Adding renderer requires touching 6+ coupled places (schema, PACK_ALIAS_KINDS, loader, alias extractor, new registry, CLI); missing any one = silent divergence.
- Override omission means renderer overrides would be inert outside CLI unless default factories accept the store.
- `additionalProperties:false` + `_filter_dynamic_element_kind_errors` show validation is schema-strict but patchy.

## Suggested approach
Subclass `CapabilityRegistry` for renderer reusing alias/override plumbing, add `renderer` to `PACK_ALIAS_KINDS` + pack.json enums/content keys in one commit, and fix the root cause by having `load_default_registry()` accept/construct `OverrideStore` instead of CLI-side patching. Add a sync test asserting schema and `permissions.py` reject/accept identical fixtures.
