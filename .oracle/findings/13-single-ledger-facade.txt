## Findings (ranked)

1. **`run_executor(request: ExecutorRunRequest, registry=None)`** — `executor/runner.py:280`; request fields at `runner.py:129-145` (`project`, `out`, `run_root`). Run creation is decided solely by `request.project`: `_prepare_project_request` (`runner.py:913-953`) returns `(None, request)` when `project` is falsy (`:917-918`); otherwise calls `prepare_project_run` (`project/run.py:145`) which writes `run.json` (`run.py:279-280`).

2. **No "no-project" mode exists.** `_resolve_project_request` (`runner.py:1041-1051`) → `selected_project` (`guidance.py:107-130`) resolves explicit → session-attached → raises `format_project_required_guidance`. A project is *always* bound via CLI: session gate (`gateway/__init__.py:227-302`), `executors run` is request-scoped (`gateway/project.py:26-30`), session slug injected via `ASTRID_GATEWAY_RESOLVED_PROJECT` (`project.py:152-176`), read in `_cmd_run` (`cli_handlers.py:381`, `capability_common.py:53-59`). `require_project` (`project/project.py:131`) only validates `project.json` — never creates runs. `maybe_gate` (`runner.py:209-234`) is a no-op outside task env.

3. **Hype spawns render as a leaf**: `steps.py:355-374` → `executor_argv` → `python -m astrid.packs.rendering.executors.render.run` (`argv.py:42-44`), via `Popen(os.environ.copy())` (`hype/runner.py:256-263`) — no `run_executor`, no `run.json`; only the orchestrator run exists. `iteration_video` calls `render_executor.render(...)` in-process (`iteration_video/run.py:147-152`, import `:25`) — also no `run.json`.

4. **Existing child-without-nested-run pattern**: task-attached child runs — `project/run.py:190-242`: with `ASTRID_TASK_PROJECT/RUN_ID/STEP_ID` env set, `prepare_project_run` reuses the parent's `run_id`, uses `step_dir_for(...)`, writes no `run.json` (`attached_to_task_run: True`); `finalize_project_run` skips the write (`run.py:421-422`). Env propagates via `subprocess_env.py:69-85,131-134`.

## Verified facts
Run creation = `request.project` set (post-resolution) AND no `ASTRID_TASK_*` env. `run_root` in the request is never honored for run creation (`runner.py:952-953` always replaces it); it's only metadata/log-capture input.

## Unknowns
Whether the facade subprocess would inherit `ASTRID_GATEWAY_RESOLVED_PROJECT`/session env from the orchestrator parent (auto-bind trigger); exact task-env values an orchestrator must set for attach.

## Risks
Session/gateway-env auto-binding creating nested `run.json`; `prepare_project_run` refusing existing non-empty dirs (`run.py:258-259`); `reject_project_with_out` (`run.py:86-88`) unless `project_was_auto_resolved`; stale output roots since `run_root` is derived, not reused.

## Suggested approach
Orchestrator invokes facade in-process/leaf with `project=None` and `ASTRID_TASK_*` env set → task-attach path (`project/run.py:190-242`) reuses the orchestrator's run context with no new `run.json`.
