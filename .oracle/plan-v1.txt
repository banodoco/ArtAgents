### 2. Additional areas to explore

1. **VibeComfy scratchpad format + digest pinning mechanics.** `vibecomfy` is an external pip dependency (`comfy_wrap` requirements pin a GitHub URL). What exactly gets digested — ready-template YAML, resolved workflow JSON, or both — and whether templates live inside this repo or in the external package, determines whether B-1b pins can be verified offline.
2. **ComfyUI CPU-mode viability on this box.** The machine is CPU-only (EPYC, no CUDA per non-goals). Must confirm which tiny/deterministic workflows actually complete under ComfyUI CPU mode versus needing a stub executor shim — this decides whether DC-1 is satisfiable "through the real subprocess binding" or needs a recorded exception.
3. **Wan2GP headless driving contract.** `grok/worker-wgp-report.md` is absent; no WGP code exists beyond the `BINDING_WGP` constant. Gate order, CLI/API surface of Wan2GP, checkpoint layout, and rollback semantics are all ungrounded — B-4 cannot be estimated tightly without recovering or reconstructing this report.
4. **Orchestrator child admission envelope shape.** `admit_child` validates `parent_task_id/parent_attempt_id/executor_id/lease_id/status_version/role/index` but the deterministic-key rule (which fields enter the idempotency key, and how `attempt_no` is excluded) is not yet pinned in code or available docs — B-3a must decide and test it first.
5. **Setup-journal placement vs product SQLite.** North Star says one SQLite file is the only structured truth. Decide whether the setup journal lives in the product DB (new migration) or as a sidecar journal file treated as replay log, not authority — this is a North-Star-sensitive design choice before B-5.
6. **Boot manifest ownership.** No "boot manifest" exists today (grep confirms). B-6 must define who emits it (application composition vs `local_bridge_server`), where it lives under the managed root, and what "registry digest" covers (`REGISTRY` entries? fixtures? both).
7. **Availability probe truthfulness vs CPU reality.** `AVAILABILITY_PROBES` currently trivially true. B-5's "truthful advertisement" must define per-binding probe predicates that stay honest on a GPU-less box without permanently disabling the catalog.

### 5. North Star check

**Principles advanced:**
- *One authority*: B-5 explicitly forces the setup-journal-vs-SQLite decision toward the single-authority rule (area 5); completion stays atomic through existing `record_completion` UoW.
- *Correctness by primitives*: B-1b reuses receipts/CAS/digest fences (named tests per primitive); B-3 builds directly on existing lease/status_version fences rather than new machinery.
- *Invisible failure*: B-3b's adversary suite and B-5's crash-mid-download resume are exactly orphan-or-replay proofs; B-1c proves no partial authority on the full path.
- *Growth by declaration*: all ~15 B-2 capabilities land as data in the existing `REGISTRY` + validator tables — zero runtime plugins, zero schema churn beyond at most one migration.
- *Honest latency*: unchanged polling/claim loop; no transport-coupled correctness introduced.

**Anti-patterns avoided:**
- No second placement authority: children admitted through the one `admit_child` gate; no mirror tables.
- No cloud fallbacks/silent swaps: availability probes (B-5) make unavailability explicit 422, never silent rerouting; B-6 fails startup closed.
- No plugin-law cosplay: bindings are three concrete constants, not an extension framework; B-1 adds a handler, not a handler *registry abstraction*.
- No just-in-case multi-user machinery: worker-child allowlist and executor-only gate already bound the surface; nothing added beyond it.
- Every abstraction names its option: the only new seam (binding handler) preserves the option to swap VibeComfy↔WGP implementations, which B-4 immediately exercises.

Aligned-progress cadence honored: small batches, writer-queue-only mutations, docs-of-record updated at each review boundary (post-B-2/B-3/B-5), commits at checkpoints, push only at phase completion, never merge to main.
