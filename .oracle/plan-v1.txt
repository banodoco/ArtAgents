# Integrated plan — unified execution plus Phase B

This file combines the two plan records that were created on the divergent
source lines. The complete source blobs remain recoverable from the two merge
parents; this file records the integrated intent and the decisions that matter at
the shared seams.

## Workstream A — unified execution

1. Migrate `task_outputs` so evidence/file outputs can complete without media,
   while preserving primary-result constraints and existing media behavior.
2. Add one generic in-process `CapabilityTaskHandler`; harvest manifests and
   staging outputs, classify media versus evidence, and complete through the
   execution service.
3. Admit executor and orchestrator `sdk.invoke` calls as kernel run+task records;
   preserve public result shape, child dependencies, events, receipts, retries,
   and terminal status.
4. Rewire direct `run.json` writers/readers. A filesystem record may remain only
   as a write-once projection stamped from kernel state; it is never authority.
5. Align run-ledger docs, SKILL, async-completion/creating-tools guidance, and
   the empirical six-capability process harness.

The source plan's open decisions are carried into integration: nullable media for
evidence in the ordered output ledger, one run plus N child tasks for orchestrators,
honest treatment of projectless `--out`, minimal evidence-primary vocabulary, and
deletion of bespoke adapters only after parity evidence.

## Workstream B — Phase B product surface

The Phase-B plan is ordered B-1 → B-2 → B-3 → B-4/B-5 → B-6:

- **B-1 binding:** pin vendored VibeComfy workflow bytes by digest, inject typed
  ports, execute a generic handler, and prove a CPU journey plus tamper refusal.
- **B-2 catalog:** add declarative validators and conformance fixtures for the
  remaining capability families, including truthful missing-prerequisite results.
- **B-3 orchestration:** use leased parents, attempt-independent deterministic
  child keys, fenced/receipted admission, replay coordination, checked transitions,
  deterministic interleaving proof, and travel/join/edit journeys.
- **B-4 Wan2GP:** vendor/pin the upstream build, run five mechanical gates, and
  prove N+1 acceptance followed by rollback to N.
- **B-5 setup:** use the fsync'd sidecar setup journal and signed versioned manifest
  for acquisition, Range resume, disk preflight, repair, deep doctor checks, and
  honest capability advertisement. The journal is replay input, not authority.
- **B-6 conformance:** compute a registry-plus-fixture digest, stamp the boot
  manifest, and fail closed on disagreement without extending frozen receipts.

## Shared integration constraints

- All completion, child admission, setup, and bridge effects retain the single
  kernel writer/UnitOfWork, receipts, events, leases, and atomicity model.
- Capability growth is declaration-first; no runtime plugin loading, cloud fallback,
  SSE, multi-user machinery, or GPU-only claim is silently introduced.
- CPU-only generation evidence may be deterministic/tiny-model; CUDA-only evidence
  is explicitly blocked and named.
- Registry/schema/fixture changes are single-writer surfaces. At each seam run the
  focused gate, then the combined suite and empirical process checks.
