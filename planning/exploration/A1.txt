### 1. Write-on-read paths (the critical finding)

**`show_timeline()` — the primary read surface — mutates disk.** In `astrid/core/timeline/crud.py:221-272`, the default `verify=False` path calls:

**`LocalFsBackend.head()` trusts a sidecar that can be stale.** At `local_fs.py:357-373`:

## Risks & conflicts

1. **`show_timeline()` is the universal read entry point and it always repairs.** The visualize command must NOT call it. Any existing code path that calls `show_timeline()` will mutate disk. The visualize command needs its own pure read path. This is a direct conflict with the plan's invariant: "never mutates the timeline, event log, asset registry, or final-output manifest."

2. **`find_timeline_by_slug()` calls `load_display_json_with_repair()`** at `paths.py:106`, which can write `display.json`. Even finding the timeline mutates disk today. The snapshot authority must use a repair-free slug lookup.

3. **Sidecar staleness in `head()` is real but bounded.** The `append_event()` path holds `LOCK_EX`, writes the event line + fsyncs, then writes the head atomically. The window between event write and head write is under the same lock, but a kill -9 mid-lock leaves the lock released. A next `head()` call with missing head file would rebuild correctly. The real risk is a head file that exists but was written before the last event — this requires a process to have appended an event, written the head, crashed, and then a second process appended another event and updated the head. Since all appends hold `LOCK_EX`, this can only happen if the first process's head write was delayed. Mitigation: always `verify_chain()` as part of snapshot creation.

4. **No `flock` on read means silent partial reads.** `_read_all_events()` at `local_fs.py:479` opens without any lock. An append happening concurrently could produce a partial last line or a file that ends mid-write. The `endswith(b"\n")` check at line 484 catches some but not all races. A version check after read (compare `head().version` to `len(events)`) would detect this.

## Elegant simplifications

1. **Pure replay + verify is sufficient; no lock needed for snapshot creation.** The `replay_projection()` at `projection.py:788` + `verify_chain()` at `local_fs.py:375` already provide a pure read path. The only missing piece is a post-read version sanity check: after reading N events, check that `head().version == N`. If not, retry. This avoids the complexity of `flock` on reads.

2. **Registry is fully derivable from events — skip the sidecar entirely.** `_registry_from_event_stream()` at `local_bridge.py:381-409` scans the log in reverse for the last `timeline.asset_registry_replaced` event. This is O(lines) in the worst case but O(1) in practice (it scans in reverse). The frozen snapshot can compute the registry hash directly from this event's payload without ever touching `registry.json` or `assets.json`.

3. **The "projected registry" is a misnomer — it's not projected, it's a full-replacement event.** `timeline.asset_registry_replaced` carries the entire registry in its payload. The projector classifies it as `non_container_read_model` and ignores it. The snapshot authority just needs the last such event's payload, hashed canonically.

4. **`head()` stale-trust can be eliminated by always reading the tail event directly.** Instead of trusting `assembly.head.json`, the snapshot authority can call `read_events()` and take `events[-1].event_id`, `events[-1].hash`, and `len(events)` as the authoritative head. The `_rebuild_head_locked()` at line 445 already does exactly this — it's just not exposed as the primary `head()` path due to performance (it reads the full log). For snapshot creation, reading all events is required anyway for hash verification, so there's zero extra cost.
