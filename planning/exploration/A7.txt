### 3. Structured-output validation, retry, session isolation, cost ceilings

**Schema-constrained output exists but is not validated client-side:** `_call_responses_api` (lines 324-332) passes `response_schema` to the OpenAI Responses API as `text.format = json_schema` with `strict: true`. However, the response text is extracted raw via `_response_text()` (lines 283-292) and **never validated against the schema on the Astrid side**. If the API returns valid JSON that doesn't match the schema, or returns free text, Astrid accepts it silently.

**No retry logic:** `_call_responses_api` (lines 339-352) makes one call and raises `AstridError` on `HTTPError` or `URLError`. No retry loop, no backoff.

**No session isolation:** Each call to `_call_responses_api` is a stateless POST with no conversation context. The plan requires "three consecutive fresh-session passes per critical fixture" (M2 brief line 71). The executor has no mechanism to guarantee a fresh session — the OpenAI Responses API is inherently stateless per request, so this is satisfied by default, but there's no explicit session-id tracking or isolation assertion.

**No cost ceilings:** The understanding pack has no cost/budget/rate-limit mechanism. The `max_output_tokens` defaults to 700 (line 532) but there is no per-run or per-fixture cost cap.

## Risks & conflicts

1. **Contact sheet vs. ordered PNGs is a hard architectural conflict.** The plan says "ordered original PNGs (not a contact sheet)" (M2 brief line 62). The executor always produces contact sheets for multi-image scenarios. If the evaluator sends 6–12 pages as a contact sheet, VLM comprehension degrades (lossy compositing, reduced resolution per frame). The plan's exit criteria require the VLM to distinguish individual PNG pages — a contact sheet defeats this.

2. **`gpt-5.4` may not exist or may not match `gpt-4o` capability.** The SKILL.md docs `best` as `gpt-4o` but code hardcodes `gpt-5.4`. If `gpt-5.4` is a typo or unavailable model, the evaluation pipeline fails silently.

3. **No schema validation on returned JSON means scoring is fragile.** The plan requires `{fixture_id, answers:[{question_id, answer_ids, time_seconds, state, confidence, abstain}]}` (decisions:997-998). If the VLM returns slightly malformed JSON, the mechanical scorer will crash without retry — and there's no client-side validation to catch this before comparison.

4. **Model revision is required by the plan but may not be available from the API.** The OpenAI Responses API response includes `model` (string) but not necessarily a revision hash. If revision isn't available, the plan's requirement ("model revision when available") is vacuously satisfied but the evidence trail is weakened.

5. **The generation-only model catalog means evaluation models live outside the registry.** If an evaluation model list is needed (for pinning, cost tracking, or `astrid models list`), it has no home in the current taxonomy.

## Elegant simplifications

1. **Skip multi-image API calls entirely — send pages one at a time.** Instead of extending `_call_responses_api` for multi-image, have the evaluator call `visual_understand` once per page (per question), then aggregate answers. This uses the existing single-image surface without modifying it, keeps the contact-sheet path untouched, and makes per-image hashes trivial to record. The cost is more API calls, but each is simpler and individually verifiable.

2. **Reuse `result_manifest.sha256_file` for input image hashing.** The manifest already computes content hashes for outputs. Call the same `sha256_file` on each input PNG before the API call and store it in the result. No new hashing infrastructure needed.

3. **Compute prompt hash as `sha256(query + json.dumps(schema, sort_keys=True))`.** No new dependency — just hash the canonical JSON form before sending.

4. **Drop the evaluation-profile registry for M2.** The plan only needs one pinned model (likely `gpt-4o` or `gpt-4o-mini`). Hardcode it in the evaluator fixture config rather than building a taxonomy extension. Defer the registry to post-M2 if multiple evaluation models become a real need.

5. **Client-side schema validation can be `jsonschema.validate(answer, fixture_answer_schema)`** — a single call after `json.loads` on the response text. If it fails, log a warning and score zero rather than crashing. This is ~5 lines and prevents the scorer from crashing on malformed VLM output.

6. **Fresh-session isolation is free with the Responses API** — each POST is stateless. Just document this rather than building session-tracking infrastructure.
