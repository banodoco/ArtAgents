## 1. Domain result envelope

Every SDK service method returns one result object that serializes to **exactly
five keys**, in any order (JSON object key order is not part of the contract):

```json
{
  "ok": true,
  "data": { "...": "domain payload" },
  "error": null,
  "receipt": { "...": "committed command receipt" },
  "idempotency_key": "<key>"
}
```

| Key | Type | Rules |
|---|---|---|
| `ok` | boolean | `true` for a committed read or mutation; `false` for any failure. |
| `data` | object or `null` | The domain payload on success (`null` for failures). |
| `error` | object or `null` | The frozen error object (§2) on failure; `null` on success. |
| `receipt` | object or `null` | The committed command receipt (§3) on **mutations**; `null` on pure reads and on failures that performed zero mutation. |
| `idempotency_key` | string | The idempotency key actually used: the caller-supplied key when one was provided, otherwise the key generated by the SDK before mutation (§4). Always present, including on failures that carried a key. |

Rules:

- No other top-level keys exist. Adding a key is a v10 amendment.
- `ok == true` implies `error is null`; `ok == false` implies `data is null`
  and `error` is a frozen error object.
- On a **replayed** mutation (identical key + identical canonical request), the
  envelope returns the already-committed receipt and result with **zero new
  rows** (§4).
- On a **mismatch** (key reused with changed canonical input), the envelope is
  an `ok: false` error with code `idempotency_mismatch`, raised **before any
  mutation** (§4).

## 2. Error taxonomy

### 2.1 Error object

Every failure carries one error object with **exactly three keys**:

```json
{
  "code": "<machine_code>",
  "message": "<human-readable string>",
  "details": { "...": "bounded JSON object" }
}
```

- `code`: one of the frozen machine codes below. Never a free-form string.
- `message`: a stable human-readable string. It must not leak SQL, filesystem
  paths, receipt internals, request bodies, or secrets.
- `details`: a **bounded** JSON object (no nested unbounded structures, no raw
  exception payloads). It may carry typed fields such as `project_id`,
  `timeline_ref`, `expected_version`, `current_version`, or `valid_options`.
  Secrets, SQL text, absolute paths, and receipt internals are prohibited in
  `details`.

### 2.2 Frozen error codes

The complete machine-code taxonomy is exactly:

| Code | Meaning |
|---|---|
| `validation_error` | Input failed schema/grammar validation. |
| `not_found` | The addressed project/timeline/media/task/run/reference/shot does not exist (or is out of the caller's project scope). |
| `conflict` | A write conflicted with current state (non-version conflict, e.g. duplicate creation). |
| `stale_version` | A CAS write supplied a stale expected version/head. |
| `terminal_state` | A mutation was attempted against a terminal (archived/cancelled/succeeded/failed) record. |
| `idempotency_mismatch` | An idempotency key was reused with different canonical input. |
| `integrity_error` | Persisted bytes/state failed verification (e.g. media hash mismatch, missing bytes). |
| `unavailable` | The writer/owner lock/service is unavailable (typed `unavailable`, e.g. a second writer process under the m4 exclusive-owner lock). |
| `internal_error` | Any unexpected exception, mapped to a bounded envelope without leaking internals. |

No other codes exist in m4. Bridge HTTP codes (`invalid_project`,
`timeline_version_conflict`, `schema_incompatible`, …) are the separate frozen
bridge vocabulary in `docs/contracts/astrid-bridge-v10.md`; the SDK service
layer maps its taxonomy above to the bridge vocabulary only inside the bridge
adapter (§6).

## 3. Exposed receipt shape

Mutations return a committed command receipt with **exactly these keys**:

```json
{
  "receipt_id": "<txn_id>",
  "command_kind": "<registered command kind, e.g. timeline.save>",
  "idempotency_key": "<key>",
  "request_hash": "<canonical semantic request hash>",
  "project_id": "<project id>",
  "project_seq": [<first_project_seq>, <last_project_seq>],
  "event_ids": ["<event id>", "..."],
  "result": { "...": "the committed command result" },
  "created_at": "<ISO-8601 UTC timestamp>"
}
```

- `receipt_id` is the transaction id (`txn_id`); `request_hash` is the
  canonical semantic hash of the request (§4); `project_seq` is the exact
  inclusive `[first, last]` project sequence range; `event_ids` are the ordered
  events appended by the command; `result` is the complete committed result.
- The receipt is a **read-only** object: callers may read it but never mutate
  it, and no SDK call accepts a receipt as a write input.
- The exposed shape is the SDK/CLI surface. **Bridge responses never expose
  receipts** (see §6 and `docs/contracts/astrid-bridge-v10.md` §7): no receipt
  field, no idempotency key, no `txn_id`/`request_hash`/`project_seq`/
  `event_ids`/`result` data is serialized by any bridge route.

## 4. Project-scoped idempotency and deterministic identity

### 4.1 Scope

Idempotency is **project-scoped**: the receipt key is the pair
`(project_id, idempotency_key)`. The same key under two different projects is
two independent commands.

### 4.2 Keys

- Every public mutation accepts an optional caller-supplied `idempotency_key`
  (non-empty string). When absent, the SDK **generates** a key before any
  mutation and returns it in the envelope's `idempotency_key` field.
- Reusing a key with **identical canonical input** replays: the committed
  receipt and result are returned with zero new rows.
- Reusing a key with **changed canonical input** (different command kind or
  different canonical request hash) raises `idempotency_mismatch` **before any
  mutation** — no sequence allocation, no event append, no projection change,
  no receipt write.

### 4.3 Canonical semantic request hashing

- The request identity is a canonical JSON hash of the **semantic command
  input**: command kind, project/global scope, and the canonicalized request
  payload (deterministic key ordering, stable serialization).
- **Generated timestamps, transaction IDs, and incidental paths are outside
  request identity**: two requests that differ only in generated `created_at`,
  a txn id, or an incidental path hash identically and are therefore replays.

### 4.4 Deterministic identity

- Stable object IDs (UUID/ULID-style) are derived **solely** from command kind,
  project/global scope, idempotency key, and child ordinal. The same
  (kind, scope, key, ordinal) always derives the same ID, so a retry creates no
  duplicate object.
- Callers never supply raw identity for derived objects; address resolution is
  repository-driven (UUID/ULID/slug within the project).

## 5. Media relation vocabulary and repository rules

### 5.1 Frozen kinds (verbatim)

The complete media relation vocabulary is exactly the five frozen kinds, in
this canonical order:

1. `derived_from`
2. `variant_of`
3. `uses_as_input`
4. `mask_for`
5. `audio_for`

### 5.2 Repository-enforced rules

The repository enforces exactly these relation rules; the service delegates
**all** relation rules to the repository:

- **Same-project ownership:** every relation edge (and every explicit
  `media_id`/locator-alias lookup) must resolve within the route project; a
  cross-project alias or edge returns `not_found`.
- **Self-edge rejection:** a media item cannot relate to itself.
- **Duplicate rejection:** a duplicate edge (same pair, same kind) is rejected.
- **One `variant_of` parent:** a media item has at most one `variant_of` parent.
- **Variant-cycle rejection:** `variant_of` cycles are rejected.

### 5.3 No direction matrix

There is **no per-kind direction matrix** and none may be invented: the service
applies the repository rules above uniformly and does not add per-kind
direction semantics beyond the frozen rules. `variant_of` direction is defined
only by the one-parent rule above.

## 6. Bridge and CLI boundaries

- The **bridge adapter** (`TimelineBridgeAdapter` and the HTTP server) calls the
  same SDK service methods, supplies the hidden deterministic bridge-derived
  save key (timeline identity + expected head + canonical payload) through the
  same atomic command, and maps stable service errors to the frozen bridge
  400/404/409/422 envelopes. It strips receipts and idempotency keys **by
  construction** from every success and error DTO.
- The **CLI** renders this exact envelope for `--json` output and concise
  human output; it accepts `--idempotency-key` on mutations and displays the
  returned key and receipt.
- The bridge error vocabulary is defined in `docs/contracts/astrid-bridge-v10.md`
  and is intentionally separate from §2.2.
